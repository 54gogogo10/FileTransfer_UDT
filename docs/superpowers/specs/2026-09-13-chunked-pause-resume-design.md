# 0x02 并发分块的暂停/继续 —— 协议设计稿（未实现）

状态：**设计稿，未排期**。2.13 开发时评估的结论：暂停分块组不只是 UI 问题——
客户端没有"哪些块已送达"的记录，暂停后"继续"若直接重发，等于从零开始，语义毫无意义。
本文给出补齐所需的最小协议改动，供后续实现参考。

## 现状

- 0x02 每个分块独立连接、独立头部（totalSize/offset/size/name），服务端用
  `ChunkTracker` 按声明偏移写入共享文件，完成判据是**区间覆盖**（不是字节累加）。
- 服务端知道 `tracker.Covers`（已收区间列表）；客户端只知道"我发了哪些块"，
  不知道哪些真正落了盘。
- GUI 在 `Concurrency > 1` 时禁用暂停按钮，正是因为没有续传依据。

## 目标

暂停一个并发分块发送后，"继续"只重发**服务端缺失的区间**，语义与 0x03/0x04
的断点续传一致：服务端权威、客户端声明仅供参考。

## 方案：覆盖率查询帧（0x0B / 0x1B）

沿用 0x0A/0x1A 能力帧模式，先协商、后查询：

### 1. 能力协商

客户端在预导阶段发 `0x0A` 能力帧，bit1 = "支持 0x0B 分块覆盖率查询"；
服务端 0x1A 的对应位回答。老对端丢弃 0x0A → 回退为"不支持"（暂停按钮照旧禁用）。

### 2. 覆盖率查询（暂停时刻或继续时刻）

```
客户端 → 服务端:
[1 byte:  0x0B]
[16 bytes: trackerKey 哈希]      // 现 trackerKey = peer|fileName，改为客户端生成
                                 // 的 16 字节会话内唯一 ID（0x02 头部需扩展携带）
服务端 → 客户端:
[1 byte:  0x1B]
[4 bytes: Int32 区间数 N]
N × [8 bytes: start][8 bytes: endExclusive]   // 已收区间，合并排序后
```

服务端从 `ChunkTracker` 读出合并区间直接回帧——纯内存操作，微秒级。
查询期间客户端照 0x03/0x04 协商点惯例放宽读超时（`LongReadWindow`）。

### 3. 继续发送

客户端把区间取补集，对每个空洞生成 `(offset, size)` 用现有 `SendChunkedAsync`
逐个补发（同一 tracker 按声明偏移写入，幂等）。空洞数为 0 时直接走完成确认。

## 服务端配套改动

1. **0x02 头部扩展**：追加 16 字节 sessionId（老对端不发送——按头部总长区分，
   与 0x03 的 verifyFlag 恒存在位同思路：新增 1 字节 flag 表示"头后有 sessionId"）。
2. **Tracker 键改造**：新会话用客户端 sessionId 作键（替代 `peer|fileName`），
   使"重连后的继续"能找到同一 tracker；保留旧键路径兼容老客户端。
3. **_tracker 生命周期**：覆盖率查询不改变现有"完成后驱逐"逻辑；查询一个
   已完成的 tracker 返回全区间（客户端据此走完成路径）。

## 客户端配套改动

1. `ConcurrentTransfer` 记录本组 16 字节 ID，所有分块头部携带。
2. 暂停：取消全部分块连接（现状已支持）+ 记录 `(file, totalSize, id)` 三元组。
3. 继续：先发 0x0B 查询 → 取补集 → 补发空洞 → 等完成判决。
4. GUI：`_numConcurrency > 1` 时按协商结果启用暂停按钮。

## 边界与风险

- **两客户端同 ID**：sessionId 由客户端随机生成，碰撞概率可忽略；服务端 tracker
  仍绑定首见连接的 peer（现逻辑），他人不可注入（沿用 0x03 的 Peer 绑定拒绝）。
- **重试语义**：现有"分块重发幂等（按偏移覆盖写）"不变，覆盖率查询只是让它
  更省，不是正确性依赖。
- **UDT**：0x02 在 UDT 上无完成判决字节（带外 ACK），0x0B 查询与其正交。

## 工作量估计

协议帧 + tracker 键改造 ≈ 1 天；客户端补集计算与状态机 ≈ 1 天；
测试（含老对端回退、跨重连续传、覆盖判据回归）≈ 1 天。
